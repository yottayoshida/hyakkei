# M0 spike: DuckDB-WASM feasibility (issue #2)

**Status: GO.** Single-threaded DuckDB-WASM handles a 100 MB CSV comfortably within the
"seconds to low tens of seconds" threshold in all three browser engines, and the memory
ceiling failure mode is a catchable JS error, not a tab crash.

## Method

- Build: **single-threaded only** (MVP/EH bundles). The COI (multi-threaded) bundle was
  excluded from the candidate set passed to `selectBundle()` — it requires COOP/COEP
  response headers, which `file://` and plain static hosting can't provide (ADR-0005).
  This matches what the shipped editor can actually use by default.
- Data: synthetic 100.3 MB / 1,645,000-row CSV (`id,date,prefecture,category,sub_category,amount,count`),
  generated by `spikes/duckdb-perf/generate-csv.mjs`.
- Load path: `fetch` → `Uint8Array` → `db.registerFileBuffer()` — this simulates a
  drag-and-dropped local file (`File.arrayBuffer()`), which is how the real editor
  acquires data, not an HTTP fetch. Localhost fetch time is reported separately and
  excluded from "load time" since it has no equivalent in the local-file-picker flow.
- Query: `CREATE TABLE t AS SELECT * FROM read_csv_auto(...)` (parse+ingest), then
  `SELECT category, prefecture, SUM(amount), COUNT(*) ... GROUP BY 1,2 ORDER BY 3 DESC LIMIT 5`
  (aggregate).
- Engines: Chromium, Firefox, WebKit via Playwright (`launchServer()` + `connect()`,
  headless). **WebKit stands in for Safari** — it's the real WebKit engine, but not
  literally Apple's Safari build; worker/thread quirks specific to Apple's build are not
  ruled out by this result.
- Memory: peak RSS (KB) sampled every 200 ms across the whole browser process tree
  (`spikes/lib/process-mem.mjs`), not just the page's JS heap — this captures WASM
  linear memory, which lives outside V8/JSC's GC heap and wouldn't show up in
  `performance.memory`.
  - **Methodology correction made during this spike**: a pure parent→child process
    walk undercounted WebKit by ~10x. On macOS, WebKit's `WebContent`/`GPU`/`Networking`
    processes are XPC services reparented to `launchd` (ppid=1), not children of the
    process Playwright hands back. Fixed by also matching processes whose executable
    path contains the browser's own `ms-playwright/<engine>-<build>` cache directory.
    Chromium and Firefox spawn their renderer/content processes as regular children, so
    this correction only changed WebKit's numbers.

## Results

| Engine | init | fetch (localhost) | registerFileBuffer | parse 100MB→table | aggregate query | peak process RSS |
|---|---|---|---|---|---|---|
| Chromium | 295–311 ms | 81–148 ms | 59–64 ms | 495–504 ms | 68–70 ms | ~930–943 MB |
| Firefox | 1073–1200 ms | 81–127 ms | 63–67 ms | **4401–4845 ms** | 518–525 ms | ~1560–1603 MB |
| WebKit | 711–795 ms | 84–126 ms | 43–45 ms | 497–525 ms | 70–71 ms | ~1182–1200 MB |

All three engines auto-selected the **EH bundle** (WASM exception handling) over MVP —
every tested engine supports it, so the smaller/faster EH path is the common case, not
just a Chromium-only win.

Bundle sizes (first-load network payload; only the selected bundle's WASM ships, not both):

| Asset | Size |
|---|---|
| JS glue bundle (esbuild, includes `apache-arrow`) | 444 KB |
| `duckdb-eh.wasm` (selected on all 3 engines here) | 34.2 MB |
| `duckdb-mvp.wasm` (fallback, not fetched unless EH unsupported) | 39.4 MB |
| EH worker script | 773 KB |

Total first-load payload when EH is selected: **~35.4 MB**, cacheable thereafter.

## Firefox is a real outlier, not noise

Firefox's CSV parse step is consistently **~9x slower** than Chromium/WebKit (4.4–4.8s vs.
~0.5s) across repeated runs, and its peak memory is ~1.6-1.7x Chromium's. This held across
3 separate full runs during this spike, so it isn't a one-off scheduling fluke. It is
still within the "seconds to low tens of seconds" go threshold for 100 MB (total pipeline
≈ 5.4s worst case), but it means **the actual go/no-go margin is set by Firefox, not
Chromium** — a 3-4x larger file could push Firefox past 10s while Chromium stays under 2s.
Firefox's console also logged a WASM exception-handling deprecation warning ("the `try`
instruction is deprecated... use `try_table`") — not currently breaking, but worth
re-checking on future DuckDB-WASM / Firefox version bumps.

## OOM behavior: PASS (catchable, not a crash)

Setting `PRAGMA memory_limit='50MB'` (well below the ~930MB-1.6GB unrestricted peak for
this dataset) before ingesting the same 100MB CSV produced, in **all three engines**:

- No tab crash (`page.on('crash')` never fired)
- No hang (result resolved within the 30s timeout)
- A catchable JS exception with an actionable message:

```
Out of Memory Error: could not allocate block of size 256.0 KiB (47.6 MiB/47.6 MiB used)
Database is launched in in-memory mode and no temporary directory is specified.
...
Possible solutions:
* Reducing the number of threads (SET threads=X)
* Disabling insertion-order preservation (SET preserve_insertion_order=false)
* Increasing the memory limit (SET memory_limit='...GB')
```

This confirms the editor can catch ingestion failures and show the user a real error
state instead of a white screen — the exact V-001/V-005 concern from the QA shift-left
review.

## Data-size limit to document publicly

Peak memory was **~9-16x the raw CSV size** (930MB-1.6GB process RSS for a 100MB file).
Treating ~3-4GB as a conservative available-memory budget for a browser tab on a modest
laptop, this spike supports publicly documenting a **guideline ceiling of roughly
200-300MB per file** for reliable operation, with the OOM path above as the honest
fallback beyond that — not a hard enforced cap, since `memory_limit` is user/environment
dependent.

## Recommendation

- **Go** on single-threaded DuckDB-WASM (EH bundle, MVP fallback) as the query engine.
- No ADR-0004 escape hatch (SQLite-WASM) triggered.
- Carry forward to M1: (a) document the ~200-300MB soft ceiling in user-facing copy,
  (b) catch and surface DuckDB's OOM error text directly in the editor's error UI — it's
  already actionable, no need to re-author it, (c) treat Firefox as the perf budget's
  binding constraint when setting any future "how big can my file be" UI copy.
