# ADR-0012: Light shaping GUI (filter, group-by/aggregate) — literal-embedded SQL, GUI-only builder state, category-gated resolver

- **Status**: Accepted (2026-07-22)
- **Deciders**: yotta

## Context

PRD F2's remaining M2 editor scope after issue 11b (column type detection + manual override): "Light shaping GUI: filter, group by + sum/count/avg — GUI generates SQL into `queries[]` (not a SQL editor)." ARCHITECTURE §4 describes the intended flow: `user builds chart in GUI -> GUI emits SQL into queries[] -> Renderer runs the query`. This PR is the resolver + GUI half of that flow; the chart/encoding half is issue 12.

ADR-0011 (issue 11b) explicitly left one decision open (RR-2): "issue 11c's query resolver may need a different CAST-application mechanism than `always TRY_CAST on read`... whichever mechanism issue 11c picks must independently decide how it interacts with a base table this PR guarantees stays unmutated." This ADR resolves that, plus the new decisions specific to a resolver that handles filters, group-by, and aggregates rather than issue 11b's single-column preview/validation.

`/plan` investigation (architect + QA + security + UX, 2 Codex MCP review rounds — one on investigation results, one on the finished plan, both real `gpt-5.5` reviews) plus an architect-run shape enumeration (`shape_complexity: high`, mirror pattern borrowed from `column-types.ts`'s `castTargetFor`/`uniqueRawAlias`) surfaced the decisions below. The shape enumeration's first pass self-declared complete; the gate's required "Missing shape: none" line was absent, so the same subagent was challenged to re-audit — a second pass then found 6 real additional gaps (G1-G6, folded into the decisions below), demonstrating the gate exists for a reason: a "looks complete" pass is not the same as a genuinely re-audited one.

A live dry-run against real DuckDB-WASM during Phase 4 implementation (not a review-stage finding — self-directed PoC discipline, same as issue 11b's) surfaced one further defect this ADR's "Runtime consistency" decision closes: an existing query's preview did not refresh when a column's type override changed elsewhere, silently showing a stale result rather than the "silent fail = zero" success metric this PR set for itself.

## Decision

### SQL generation: literal embedding (`quoteStringLiteral` + `TRY_CAST`), not prepared statements

DuckDB-WASM exposes a real prepared-statement API (`conn.prepare(text)` -> `AsyncPreparedStatement.query(...params)`), and Security's Phase 2 investigation initially proposed it as optional defense-in-depth for the preview path. Rejected: `packages/schema/src/baked.ts`'s bake contract executes `Query.sql` as a **self-contained string** with no side-channel parameter store — a `?` placeholder cannot be persisted into a shared `dashboard.json` at all. Every filter value (including numeric and date values, not just text) is embedded via `quoteStringLiteral`, wrapped in `TRY_CAST(... AS <target>)` when the column's effective category isn't `text` (`typedValueLiteral`). Codex plan review supported this as the right call, not a rushed shortcut — a second, prepared-statement-based validation path would only add a second thing to keep in sync with the persisted, string-only path.

### TRY_CAST applied at every position — WHERE, GROUP BY, and the aggregate argument — except COUNT

An overridden column gets `TRY_CAST(col AS castTargetFor(effectiveCategory))` applied consistently across all three positions a resolved query can reference it. **COUNT is the deliberate exception**: it uses the raw column reference (`quoteIdentifier(column)`, no cast), because Excel PivotTable's "個数" (count) counts non-blank cells in the raw data, not "cast-successful" cells — a `TRY_CAST`-wrapped COUNT would silently redefine what "個数" means relative to the mental model the UX design deliberately borrows. My own first implementation got this backwards twice, both caught by my own unit tests before any review: it initially excluded "other"-category columns from COUNT entirely (COUNT needs no type interpretation at all — it should work on any existing column), and separately left the GROUP BY position un-cast while every other position was, violating this decision's own "every position, consistently" premise. Both were fixed in the same implementation pass, not carried to review as known gaps.

### A `"text"`-category filter COMPARISON always `TRY_CAST`s the column to VARCHAR, even with no active override

`typedColumnRef`'s "no active override, stay a bare reference" path assumes the column's native DuckDB type is already exactly what the comparison needs — true for `number`/`date` (an override always wraps those in the right cast) and true for a genuinely `Utf8`/`LargeUtf8` column, but **false** for a native `BOOLEAN` or `NULL`-typed column: `arrowTypeCategory` (issue 11b) buckets both into `"text"` for display purposes only (this app's 3-category taxonomy has no boolean category), while their actual DuckDB column type stays `BOOLEAN`/`NULL`, not `VARCHAR`. Phase 8 QA found this live (Major severity, confirmed with a real `.xlsx` fixture carrying a genuine ExcelJS boolean cell — not a `"true"`/`"false"` text string, which this app's CSV/xlsx ingestion never types as native `BOOLEAN` on its own): comparing a raw `BOOLEAN` column against any string literal throws (`"flag" = ''` → `Conversion Error: Could not convert string '' to BOOL`; a `contains`/`not_contains` filter → a `like_escape` Binder Error) — including via the query builder's own **default new-filter value** (`{operator: "eq", value: ""}`), making this reachable by the single most ordinary action a user can take (add a filter, pick that column). `filterConditionSql` now always emits `TRY_CAST(col AS VARCHAR)` for a `"text"`-category comparison (not `is_null`/`is_not_null`, which need no cast at all), regardless of whether an override is active — for a genuine VARCHAR column this is a no-op; for a `BOOLEAN`/`NULL` column masquerading as `"text"`, it makes the comparison well-defined (`TRY_CAST(flag AS VARCHAR) = 'true'` works; an unmatched literal like `''` correctly evaluates to no rows instead of throwing).

This same defect compounded with a second, more general gap App.tsx's `refreshQueryPreview` had independently of this specific bug: its `catch` block only cleared `previewPending`, leaving `previewRows`/`previewColumns`/`diagnostics` at their PRIOR (stale) values on any unexpected query failure — so the boolean-filter throw above was silently swallowed and the UI kept showing the unfiltered result with no error indication at all, the exact "silent fail" this PR's own success metric names as unacceptable. Fixed at the general level, not just for this one trigger: any caught, non-`RangeError` query failure now also clears `previewRows`/`previewColumns`/`diagnostics` to their "nothing resolved" defaults, so a future unexpected DuckDB error (whatever its cause) fails visibly-empty rather than silently-stale.

### Measure alias collision avoidance extends to real column names and group-by columns, not just other measure aliases

A measure's default alias (`<aggregate>_<column>`, e.g. `sum_amount`) is generated by `uniqueRawAlias` (promoted from module-private to `export` in `column-types.ts` specifically for this reuse — ADR-0011's own "Builder responsibility split" note anticipated this). The shape enumeration's first pass assumed the collision risk was scoped to "two measures producing the same alias." A live PoC against real DuckDB-WASM (`register-harness.html`) found the actual risk is broader and the actual failure mode is worse than assumed: `SELECT sum_amount, SUM(amount) AS sum_amount FROM t GROUP BY sum_amount` — a real column named exactly `sum_amount` colliding with a measure's auto-generated alias — does not simply have one value silently win. The colliding result key ends up holding a raw `Uint32Array` (an Arrow buffer fragment), not a plain number or string: outright data corruption, not value loss. `uniqueRawAlias`'s `taken` set was extended to include every real column name and every accepted group-by column, not just previously-issued measure aliases, closing this before it could reach a user-visible query.

### Filter value validity and measure cast-failure counts are surfaced through a dedicated diagnostics query, not inferred from row counts alone

`buildQueryDiagnosticsSql` returns, in one round-trip alongside the preview: `total_count`, `matched_count` (post-WHERE), a `filter_<i>_value_invalid` boolean per filter (does the literal VALUE itself parse as the column's category, independent of any row's data), and a `<column>_excluded_count` per sum/avg measure (rows where the raw value is non-null but the cast failed). The `filter_<i>_value_invalid` check exists because a filter like `amount > "abc"` on a number column produces `TRY_CAST('abc' AS DOUBLE) = NULL`, silently excluding every row — visually identical to "0 legitimately matching rows" without this diagnostic to distinguish a typo from a genuine empty result.

### LIKE wildcard characters in a `contains`/`not_contains` filter value are escaped, not passed through as literal SQL wildcards

`quoteStringLiteral` makes a value SQL-injection-safe but does not touch `%`/`_`, which are meaningful to `LIKE` regardless of quoting. `likePatternLiteral` escapes `\`/`%`/`_` (backslash first, to avoid double-escaping) and every `contains`/`not_contains` filter compiles with an explicit `ESCAPE '\'` clause — without this, searching for the literal text `"50%"` would also match unrelated rows like `"50 percent off"`.

### sum/avg require an effective category of `number`; COUNT is the only aggregate offered otherwise

The shape enumeration's first pass modeled this gate as "not `date`" (mirroring an early framing of issue 11b's own precision-loss risk). The second pass generalized it correctly: an "other"-category column (List/Struct/Binary/Time/Interval — override-ineligible, same set issue 11b's type-override `<select>` already disables) fails `SUM(VARCHAR)`-shaped binder errors exactly like a `date` column would. The gate is `category === "number" ? [sum, count, avg] : [count]` — simple, and correct for every non-number category at once rather than enumerating exclusions one at a time.

### Runtime consistency: an override change elsewhere refreshes every existing query on that source, and a category/aggregate mismatch is visibly warned, not silently dropped

This PR's own success metric was "dangling column references and category<->operator mismatches are detected and warned at runtime — zero silent failures." The first implementation pass met this for edits made **through the query builder itself** (any control change re-resolves against the current override map, and the resolver already silently excludes a now-invalid filter/measure the same way it excludes a dangling column reference) but missed the case where the override changes **elsewhere** — the source card's own type-override `<select>`, not the query builder. A live dry-run confirmed the gap concretely: after overriding a column away from `number` while an existing query had a `sum` measure on it, the query's preview kept showing the prior override's numeric result, unchanged, until the user happened to touch that specific query's own controls again.

Closed with two changes, both scoped to the app layer (no schema/resolver change): `handleOverrideChange` (App.tsx) now sweeps every query referencing the affected source and re-runs `refreshQueryPreview` (a function extracted from what was previously `handleQueryBuilderChange`'s own body, now shared by both trigger paths) against each query's *unchanged* `builderState` and the *new* override map — the resolver's own category gate does the rest, since a measure that no longer fits its column's category is already dropped from the generated SQL the same way a dangling reference is. `QueryBuilder.tsx` separately renders a visible warning ("列の種類が変わったため、この集計は結果から除外されています") whenever a measure's stored `aggregate` is no longer among the options its column's *current* effective category offers — the UI-visible half of the same fix, so a measure disappearing from the result comes with a reason, not silence.

### Schema: `Query.builderState`, additive, array-shaped, all three sub-arrays required (not each independently optional)

Mirrors `Source.typeOverrides`'s own established design (ADR-0011) exactly: `BuilderState = { filters: FilterCondition[], groupBy: string[], measures: Measure[] }`, all three fields **required** `Type.Array` (not `Type.Optional` each), with only the whole `builderState` field `Type.Optional` on `Query`. This makes `{}` (all three arrays missing) Ajv-invalid while `{filters:[],groupBy:[],measures:[]}` ("nothing configured yet") is valid — a deliberate two-state distinction the shape enumeration's G1 finding confirmed was worth pinning explicitly in tests, not just implying from the type. `groupBy` is an array of column-name **values**, never object keys — the same prototype-pollution avoidance discipline `typeOverrides` already established, extended to a second field. `FilterCondition.value` is `Type.Optional(Type.String())`: `undefined` means "this condition is incomplete, exclude from WHERE" (a distinct UI state, not an error); `""` (empty string) is a complete, meaningful "match a blank cell" condition — schema does not reject it.

`Query.sql` and `Query.builderState` are always recompiled together on every GUI edit (no separate "hand-edited SQL wins" resolution in v1) — when `builderState` is present, `sql` is always its freshly-compiled output, so the two fields cannot drift apart within a session.

### Closed-enum, fail-fast lookups for operator/aggregate SQL, mirroring `castTargetFor`

`operatorSqlFor`/`aggregateFnFor` use the identical discipline `castTargetFor` established in ADR-0011: `Object.hasOwn` (not a bare index or `in`, which resolves `Object.prototype` members) against a fixed `Record`, throwing a `RangeError` before any SQL text is built if the value isn't one of the union's literals. TypeScript's own `FilterOperator`/`AggregateFn` unions already restrict every real call site through the GUI; this throw is the same defense-in-depth ADR-0011 established for a value that bypasses that restriction (a future `dashboard.json`-driven load, once F7 exists).

## Alternatives considered

| Option | Rejected because |
|---|---|
| Prepared statements (`conn.prepare()`) for filter values | `baked.ts`'s bake contract requires `Query.sql` to be a self-contained string; a `?` placeholder has no persisted parameter store to bind against |
| `builderState` -> intermediate `QueryPlan` AST -> SQL, instead of direct string building | Codex plan review's own assessment: over-engineered for this PR's scope; deferred, not designed around now |
| Modeling the sum/avg category gate as "not date" | Shape enumeration G5: an "other"-category column (List/Struct/Binary/etc.) fails identically to `date`; "number-only, else count" is simpler and correct for every non-number case at once |
| COUNT going through the same `TRY_CAST`-wrapped column reference as SUM/AVG | Would silently redefine "個数" as "cast-successful count" rather than Excel-parity's "non-blank raw cell count" — the UX design's own borrowed mental model |
| Measure alias collision avoidance scoped to "other measure aliases" only | Live PoC: a real column name or group-by column can collide too, and the actual failure mode is a corrupted `Uint32Array` result key, not just one value silently winning |
| Inferring "0 matched rows" as always meaning "no data satisfies the filter" | A filter value that doesn't parse as its column's category (a typo) produces the same visible 0-row result; `buildQueryDiagnosticsSql`'s per-filter `value_invalid` check distinguishes the two causes |
| Leaving a stale query preview as-is until the user next edits that query | Live dry-run: silently showed a numerically wrong result (the prior override's cast) with no indication anything had gone stale — missed this PR's own "silent fail = zero" success metric |
| GROUP BY resolving to a SELECT-list alias (`GROUP BY ALL` or bare alias reference) | Dialect-ambiguous whether an alias resolves to itself or a same-named source column; an explicit, repeated `TRY_CAST(...)` expression in both SELECT and GROUP BY is more auditable for persisted, hand-readable SQL |
| Schema-layer validation of dangling `builderState` column references | `dashboard.json` never persists column metadata — `validateDashboardReferences` (schema layer) has no data to check a column reference against. Left as a runtime-layer (App.tsx, live `columnMeta`) concern instead, deferred to whenever F7 (save/load) exists to make it reachable at all |

## Residual risks (accepted for this PR)

- **RR-6 — `Query.builderState` round-tripping through a saved-and-reopened `dashboard.json` is not verified.** F7 (save/open UI) does not exist yet (confirmed, same as ADR-0011's own equivalent scope boundary) — this PR's acceptance bar is the schema shape existing and round-tripping (Ajv-verified) plus the full detect -> filter/group/aggregate -> preview loop working live, within a session, against real DuckDB-WASM (all 3 browsers). "Save the file, reopen it, the query is still there and still valid against a possibly-changed source" is explicitly deferred to F7, not assumed.
- **RR-7 — A stale `contains`/`not_contains` filter operator surviving a category change (text -> number/date) does not crash, but its result is only as sensible as DuckDB's own implicit numeric/temporal-to-VARCHAR cast for `LIKE`.** Confirmed via live PoC: no binder-time error occurs (unlike the analogous HUGEINT/regexp_matches binder-time failures ADR-0011 found and fixed for its own validation queries), and a substring match against DuckDB's own canonical stringification is a defensible, if unusual, result. Unlike the sum/avg-aggregate mismatch (which is silently dropped and now visibly warned), this path is not gated or warned — accepted as a narrower, non-crashing, low-likelihood edge case (requires overriding a column's category while a `contains`/`not_contains` filter targets it) rather than closed with additional UI-layer logic.
- **RR-8 — Measure alias collision avoidance and category gating are resolver-level defenses; they do not prevent every possible confusing (but non-corrupting, non-crashing) SQL shape a sufficiently adversarial hand-edited `builderState` could produce**, once F7 makes hand-editing `dashboard.json` reachable. Consistent with ADR-0011's own posture (RR-2 there): a resolver's safety net is closed-enum lookups + `quoteIdentifier`/`quoteStringLiteral` discipline against SQL injection specifically, not a general-purpose "is this a sensible query" validator.
- **RR-9 — `uniqueRawAlias`'s collision avoidance (`taken.has(alias)`) is exact-case string matching, while DuckDB's own identifier resolution is case-insensitive at the CATALOG level** (confirmed live: `CREATE TABLE t ("amount" INTEGER, "AMOUNT" INTEGER)` throws `Catalog Error: Column with name AMOUNT already exists!`). Codex review (Phase 6-A, Round 1) flagged this as a possible gap; live-tested and refuted for THIS PR's own consumption path — a real column and a case-differing generated alias in the SAME `SELECT` list round-trip as two distinct, uncorrupted values (`{"SUM_AMOUNT": 100, "sum_amount": 12}`, no merge, no error) — because DuckDB's case-folding governs catalog/binder name resolution, not SELECT-list output-alias identity, and this resolver never wraps its own output in a further SQL layer that would re-resolve those aliases as identifiers. Codex's own follow-up (Round 2, agreeing the finding doesn't block this PR) named the concrete scenario where it WOULD start to matter: a future SQL layer (issue 12's chart/encoding step, or a bake step) that itself references `Query.sql`'s OUTPUT columns by identifier (not just by reading Arrow field names positionally/by-name from a result, as this PR's own preview does) could hit DuckDB's case-insensitive binding when two output columns differ only by case. Accepted as out of this PR's scope — flagged here so issue 12/bake work defines its own case-folded output-name policy before wrapping a generated query in further SQL, rather than rediscovering this the same way this PR did.
- **RR-10 — The "override wins over auto-detected category" rule (`effectiveCategory`) and the "sum/avg require an effective category of `number`" gate are each implemented TWICE — once in the resolver (`query-sql.ts`), once in the UI (`QueryBuilder.tsx`)** — flagged independently by 3 of `/simplify`'s 4 review angles (Reuse, Simplification, Altitude), the strongest convergence signal this PR's own review process produced. Not merged: the app entry chunk must never statically import from `packages/core/src/datasource` (issue #54 bundle isolation — that module pulls in duckdb-wasm/exceljs/apache-arrow at load time), and `QueryBuilder.tsx` needs this rule SYNCHRONOUSLY during render, before the lazy `loadDataLayer()` boundary could ever resolve — the same constraint that already forced `castTargetFor`/`uniqueRawAlias` to be reused via the async `layer.datasource.*` boundary, which a render-time UI computation cannot use. `@hyakkei/schema` was considered as a shared, dependency-free home (Altitude's suggestion) but rejected on inspection: `@hyakkei/core` depends on `@hyakkei/schema`, not the other way around, and `ColumnCategory`/`ColumnMeta` are core datasource-detection concepts, not schema/persistence ones — moving them would be a package-ownership change, not a Phase 7 cleanup. Accepted duplication, each copy commented to cross-reference the other; a genuine fix (e.g. a new arrow-free `package.json` export subpath core could expose) is a platform-level change out of this PR's scope.
- **RR-11 — The aggregate-mismatch warning (`QueryBuilder.tsx`) only covers ONE of the resolver's two reasons a measure can be silently dropped** (a category no longer supporting the aggregate; not a dangling/nonexistent column reference) — flagged by `/simplify`'s Altitude review. Confirmed not user-reachable this session: a column disappearing from `columnMeta` only happens via source deletion, which already orphans (deletes) every query referencing that source (`handleSourceDelete`), so a `builderState` referencing a column that no longer exists cannot currently arise through the GUI. Reachable only once F7 (save/open) allows a hand-edited `dashboard.json` to carry a dangling reference into a live session. Deferred, not implemented: the fix (a shared `measureDropReason(measure, columnMeta, overrides): "dangling" | "category-mismatch" | null` the resolver and UI both consult) is real but not worth building against a currently-unreachable path; revisit when F7 exists.
- **RR-12 — An aggregated query's status message reports the pre-aggregation matched row count, not the number of result groups shown in the table** (QA Phase 8, Minor). `buildQueryDiagnosticsSql`'s `matched_count` counts SOURCE rows the WHERE clause keeps (correct and useful information — "how many of your rows fed this aggregation"), but the status copy ("該当N行") sits directly above a table showing GROUPED rows, and a non-technical user could read the two numbers as contradicting each other (e.g. "該当3行" above a 2-row grouped table). Functionally correct, not misleading about data integrity — deferred as a copy/wording clarity issue (distinguishing "N source rows -> M groups" phrasing for the aggregated case) rather than a defect in what's computed, since the UX-designer subagent's Phase 2 review of this exact status message did not flag this distinction as needed and reworking it is a scope addition, not a fix.
- **RR-13 — A raw `SELECT *` preview (empty `builderState`, no measures) can show a `BIGINT` value silently rounded past `Number`'s 53-bit exact-integer range** (QA Phase 8, Minor/informational; confirmed live: a native `9007199254740993` displays as `9007199254740992`). This is the SAME precision boundary ADR-0011's RR-5 already accepts for issue 11b's override-validation path (`rowToPlainObject`'s bigint->Number conversion) — newly exposed here because the query builder's own degenerate "nothing configured yet" preview reads raw table data through the identical conversion, with no advisory mechanism of its own (issue 11b's precision advisory only fires during override validation, not a bare preview read). Accepted under the same reasoning RR-5 already established; not a new class of risk, just a new surface where the existing one is visible.

## Consequences

- (+) A non-technical user (PRD's Sato-san persona) builds a filtered, grouped, aggregated summary entirely through category-gated `<select>`s and inputs — zero SQL keystrokes, matching the "not a SQL editor" framing PRD F2 requires.
- (+) Every SQL-generation code path (identifier, operator, aggregate function, filter value) goes through a closed, fail-fast mechanism — no template-literal interpolation of untrusted or enum-typed data anywhere in `query-sql.ts`.
- (+) A measure's default alias is a stable, collision-safe, forward contract issue 12's chart-encoding UI can reference by name without its own collision-avoidance logic.
- (+) "Silent fail" scenarios this PR set out to close — dangling references, cast-failure exclusions, filter-value typos, and (after the runtime-consistency fix) override changes made elsewhere — are all now either prevented or visibly surfaced, not just prevented at the SQL-generation layer while staying invisible at the UI layer.
- (−) `Query.builderState`'s shape is now a de facto forward compatibility contract for F7's eventual save/load and for issue 12's chart tiles, decided without either of those consumers existing yet to validate against — mitigated by following the exact additive/array-shaped precedent ADR-0011 already established and proved out.
- (−) RR-7 leaves one narrow, non-crashing edge case (a stale `contains` operator on a re-categorized column) without a dedicated UI warning, unlike the equivalent aggregate-mismatch case — an intentional scope line, not an oversight.
