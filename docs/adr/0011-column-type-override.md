# ADR-0011: Column type detection + manual override — Arrow typeId detection, closed-lookup CAST, delta-only schema contract

- **Status**: Accepted (2026-07-22)
- **Deciders**: yotta

## Context

PRD F2 ("Data preview + light shaping: Column types...") is the first M2 editor PR after the single-SPA shell (ADR-0010). CSV/xlsx/parquet registration already produces a semantic type per column (`ColumnMeta.type`, an apache-arrow display string, e.g. `Int64`/`Date32<DAY>`), but the editor's preview (`RegisteredSummary.tsx`) showed only column names — no type, no way to correct a misdetection. Real government data hits this: a postal-code or business-registration-number column auto-detects as numeric and loses its leading zero, or a mixed-content column (some rows redacted as text) auto-detects as text when the user wants to treat it as numeric for charting.

`/plan` investigation (architect + QA + security + UX, one Codex MCP review round on investigation results, one on the finished plan — Codex auth was restored mid-session, both were real model reviews, not proxy) plus an architect-run shape enumeration (`shape_complexity: high`, mirror pattern borrowed from `identifier.ts`'s escaping discipline) surfaced the decisions this ADR records. A further Codex review round after implementation (Phase 6-A) found and fixed one P0 and three P1 defects the plan's design intent did not fully carry into the first implementation pass — those fixes are folded into the decisions below, not listed as a separate correction, since they close gaps in *this* PR's own thesis rather than reversing a decision.

A subsequent `/code-review` pass (10 independent finder angles, Phase 6-C) found several more defects after implementation: a `__proto__`-shaped prototype-pollution reintroduction in the preview-row merge, a conflated try/catch that let a preview-refresh failure overwrite an already-correct validation result, a `"failed"` validation status that was computed but never rendered, and two genuine data-integrity gaps in the validation model itself (silent DOUBLE precision loss, silent DATE timezone-offset loss). The first three are implementation bugs, fixed without a design change. The last two motivated a real design addition — recorded below as its own decision, not folded into an existing one, since it adds a new diagnostic axis this ADR did not originally have.

## Decision

### Detection: Arrow `typeId`-based classification, not string parsing — `arrowTypeCategory()`

`ColumnMeta.type` is apache-arrow's own `DataType.toString()` display string, used elsewhere in this codebase for *display* only, never for branching. `arrowTypeCategory()` (`packages/core/src/datasource/column-types.ts`) instead uses Arrow's static `DataType.is*` guards (`isInt`/`isFloat`/`isDecimal` → `"number"`; `isDate`/`isTimestamp` → `"date"`; `isUtf8`/`isLargeUtf8`/`isBool`/`isNull` → `"text"`; everything else → `"other"`), recursing through `Dictionary`-encoded columns first. PoC confirmed empirically (2026-07-22) that apache-arrow's own `tableFromArrays()` dictionary-encodes plain string columns by default — the Dictionary-recursion branch is the **common** path for text columns read back from a real DuckDB Arrow result, not a defensive edge case.

**Rejected: string-parsing `type.toString()`'s output** (e.g. matching `/^Int/`). The display format has already shifted shape across this codebase's own history and is apache-arrow's formatting choice, not a contract; the typed guards are the stable, versioned API surface.

### 3 user-facing categories only — `text` | `number` | `date`, plus a non-overridable `"other"`

PRD F2 asks for "column types" as a light-touch concept ("this is a date"), not a SQL type picker — Hick's Law argues against widening past 3 choices, and DOUBLE already covers integer/decimal for this PR's charting-oriented use. Binary/Time/Interval/List/Struct/Union/Map/FixedSize* Arrow types fall through to `"other"`: none fit the 3 categories without a lossy or misleading cast, so the `<select>` disables itself for these columns rather than offering a choice that would silently do the wrong thing. Splitting `number` into integer/decimal, or adding a `timestamp` category, are both additive (enum member + `CAST_TARGET` entry) — deferred, not designed around now.

### CAST target: closed lookup that **throws on an unrecognized category**, never a template-literal interpolation

`CAST(col AS <type>)`'s type position cannot be escaped the way an identifier or string literal can be — quoting a type keyword (`CAST(x AS "DOUBLE")`) is different, usually broken, SQL. `CAST_TARGET: Record<ColumnCategory, string>` is the only place a category maps to a DuckDB type keyword; every builder goes through `castTargetFor(category)`, which does an `Object.hasOwn` check (not a bare index or `in`, which would resolve `Object.prototype` members like `"toString"` to a function reference instead of failing) and **throws a `RangeError` before returning any SQL** if `category` is not one of the 3 literals. This was the one Codex-review-found P0: the first implementation pass indexed `CAST_TARGET` directly, which degrades to `undefined` for an out-of-union value and let `CAST(... AS undefined)` reach DuckDB's own parser instead of failing at the point the unsafe value was about to touch SQL text at all. TypeScript's `ColumnCategory` union already restricts every real call site — this throw is the defense-in-depth for the one case that bypasses it: a value read back from a shared `dashboard.json` (Ajv-validated at parse time, but this function must not assume that validation already ran) or a future upstream bug.

### Apply model: "always re-derive via `TRY_CAST`," never mutate the registered table

Override application re-selects the table with `TRY_CAST(col AS target)` for overridden columns, leaving the underlying `CREATE TABLE`d data untouched. **Rejected: `CREATE VIEW`/`CREATE TABLE AS` materializing a typed relation under the same id.** `register()` is a plain `CREATE TABLE` (not `CREATE OR REPLACE`), and `App.tsx`'s existing delete flow issues `DROP TABLE IF EXISTS <id>` directly against that name — a view-based approach would need `ALTER TABLE RENAME` + `CREATE VIEW` bookkeeping, turn `DROP TABLE` into a type mismatch (`DROP VIEW`), and — worse — a `number→text→number` override round-trip would re-cast from an already-cast (lossy) intermediate rather than the original raw value. The chosen model keeps every override fully reversible from the source of truth at zero cost to the existing register/delete contract.

### Validation query: `COUNT(...) FILTER (WHERE ...)`, not `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`

PoC (2026-07-22, real DuckDB-WASM via `register-harness.html`) found that `SUM` over a `CASE`-derived 0/1 defaults to `HUGEINT` (128-bit) in DuckDB, which this codebase's `rowToPlainObject` does not surface as a plain JS number — it arrives as a multi-limb object (`{"0":5,"1":0,...}`), silently breaking the count display. `COUNT(col) FILTER (WHERE TRY_CAST(col AS target) IS NULL)` is a plain integer-typed aggregate, round-trips cleanly, and is simpler SQL besides.

### Preview raw-value recovery: both cast and raw values selected in the SAME query, under a collision-checked alias

`TRY_CAST` returns `NULL` on failure — indistinguishable from a genuinely-null cell in the typed result alone. `buildTypedPreviewSql` selects an overridden column twice: once cast under its real name, once raw under a synthetic alias (`__hyakkei_raw_<index>__`), in one query — not two separately-issued queries merged client-side by row position, since DuckDB gives no row-ordering guarantee across two independent `LIMIT`-bounded selects without an `ORDER BY` key. The alias is checked against every real column name **and** every alias already handed out in the same call before use (Codex review P1): column names are arbitrary data, so an index-derived candidate alias is not automatically collision-free — a real column could legally be named exactly `__hyakkei_raw_0__`.

### Generation guard: registration-scoped, not just per-column

Override validation/preview queries are async and can resolve out of order (`IntakeApp.tsx`'s existing `generationRef` pattern, applied here). Two Codex-review-found races shaped the final key design:

- **Preview freshness must be tracked per-source, not per-column** (P1): the preview re-selects the WHOLE row using every currently-active override, so two different columns' override changes each kick off their own preview refresh — whichever is issued LAST is not necessarily the one that resolves last. A single source-scoped preview-generation counter (not the triggering column's own counter) makes "is this preview result still the most recently requested one" one unambiguous check.
- **A reused table id can ABA a stale result back to "current"** (P1): `identifier.ts` can hand the same table id to a brand-new registration after a delete. Resetting a per-(tableId, column) counter on delete, then letting a fresh registration's first override restart it at the same value an old in-flight query had already captured, lets that stale query's result look current again once it finally resolves. Every generation key is namespaced by a monotonic, never-reused **registration sequence number** (assigned once per successful registration, independent of table id reuse) in addition to table id and column — a reused table id gets a brand-new sequence, so its keys can never collide with the previous registration's, regardless of any individual counter's numeric value.

### Schema: `Source.typeOverrides?: Array<{column, category}>`, delta-only, array-shaped, additive

`typeOverrides` sits at `Source`'s top level (sibling of `ref`, not nested inside it — format-independent shaping, not a format-specific ingestion parameter), on every `Source` variant (`fileSource()`'s 3 formats + `UrlSource` — every variant produces a queryable table, so all can carry it). Delta-only: only overridden columns are listed; detection itself is a runtime computation re-derived from the live table each session, so it cannot go stale relative to swapped-in data. Array, not a column-name-keyed object/`SafeRecord`: column names are data (may legally be `__proto__`/`constructor`/whitespace/CJK), and keeping them out of JS-object-key position removes the prototype-pollution surface a keyed form would need a dedicated property-name guard for. `Type.Optional` (additive) — existing dashboard.json files (none of which have this field, confirmed by a whole-repo grep at design time) decode unaffected.

**Duplicate `column` entries are schema-valid** (arrays permit them; JSON Schema has no cross-item uniqueness keyword scoped to one field) but **resolve as last-wins at runtime, with a schema-adjacent advisory**: `validateDashboardReferences` (`packages/schema/src/validate.ts`) now flags a duplicate-column `typeOverrides` entry the same way it already flags a duplicate `Source`/`Query`/`Chart` id (`kind: "duplicate"`), using a `Set` (not a plain object) to stay clear of the same prototype-pollution class this file guards elsewhere. This closes a gap Codex review found: the schema's own doc comment originally promised this advisory before it was actually implemented.

### Persistence scope for this PR: schema contract only, not F7's save/open UI

The whole app currently has **no dashboard.json save/reload implementation at all** (confirmed by grep: zero hits for `localStorage`/`saveDashboard`/`Value.Check`/`Value.Decode` in `packages/app/src`) — a fact two independent Phase 2 investigations (architect and QA) reached separately. This PR's acceptance bar is therefore: the schema field exists and round-trips (Ajv-verified), and the detect → override → validate → re-preview loop works end-to-end *within a session* (verified live, real DuckDB-WASM, all 3 browsers). "Save the file, reopen it, the override is still there" is **not** verified here — it cannot be, without F7 existing first — and is explicitly deferred, not silently assumed.

### Precision/timezone advisory: an orthogonal diagnostic, additive to the pass/fail cast outcome — `buildNumberPrecisionCheckSql()` / `buildDateOffsetCheckSql()`

A `TRY_CAST` succeeding is not the same as preserving the value exactly. Two concrete gaps in the validation model itself (`/code-review` Angle D, confirmed via real DuckDB-WASM execution, not assumed):

- **DOUBLE precision loss.** IEEE 754 double has only 53 bits of exact integer precision (~9.007e15, 15-16 decimal digits). A long integer-like id (e.g. a 17-digit corporate/invoice number) overridden to `number` casts "successfully" to `DOUBLE`, but silently rounds — directly undermining this PR's own motivating postal-code/id-column use case, and `uncastable_count` stays 0 the whole time since the cast did not fail, it lied about the result.
- **DATE timezone-offset loss.** `TRY_CAST(... AS DATE)` truncates any embedded time-of-day AND discards any UTC offset without normalizing to it first — `'2024-03-04T01:00:00+09:00'` and the same literal with `-09:00` both truncate to the same `2024-03-04`, even though a UTC-normalized calendar day could genuinely differ near a midnight boundary. Sibling risk to RR-1 (below) but a distinct, deterministic mechanism.

Both are detected via an additional, category-specific query issued alongside the existing validation/sample queries (`null` for `text`, where neither risk applies) and surfaced as an optional `advisory` field on `ColumnValidationState`'s `"valid"`/`"warning"` variants — orthogonal to (not a replacement for) the existing uncastable-count outcome, since a column can be `"valid"` (zero uncastable values) and still carry an advisory. Detection mechanisms, chosen for being decidable without introducing a floating judgment call of our own:

- **Precision loss**: a HUGEINT round-trip (`TRY_CAST(TRY_CAST(x AS DOUBLE) AS HUGEINT) <> TRY_CAST(x AS HUGEINT)`), gated to values matching `^-?[0-9]+$` (an integer-shaped literal) — a value that casts cleanly to DuckDB's 128-bit exact integer type but does not survive DOUBLE-and-back has provably lost precision. Only the count crosses into JS (the same shape already proven safe for the existing validation counts) — no risk of the HUGEINT/JS serialization gap the `SUM(CASE...)` PoC finding hit earlier in this same PR, since no HUGEINT *value* is ever read back into JS here.
- **Timezone-offset loss**: a plain textual pattern match (`regexp_matches(..., '([zZ]|[+-][0-9]{2}:?[0-9]{2})$')`) for an explicit `Z`/offset suffix on the source text — deterministic, not a timezone-conversion semantic of our own to get subtly wrong.

**A real e2e run against actual DuckDB-WASM caught a genuine defect in the first version of both queries** (not a hypothetical — this is exactly the PoC-before-commit discipline this PR's own validation-query design already established for the `SUM(CASE...)`/HUGEINT finding): a column DuckDB's CSV sniffer already types as `DATE`/`TIMESTAMP` (or one a user overrides away from its auto-detected category) has no registered *direct* cast to `HUGEINT`, and `regexp_matches` requires a `VARCHAR` argument — both threw a **binder-time** error (not a graceful `NULL`, which `TRY_CAST` alone would have suppressed) the first time either query ran against a column shaped that way. Both builders now go through `CAST(col AS VARCHAR)` first: for a genuinely textual column this is a no-op identity cast (original behavior unchanged); for an already-native numeric/temporal column, DuckDB's own canonical stringification either still round-trips exactly (no advisory raised) or simply isn't shaped like the thing being checked for (correctly not flagged) — never a crash.

This also surfaced a genuine, distinct scope boundary for the timezone-offset check specifically: for a column DuckDB's sniffer **already** parsed as a native `TIMESTAMP` at CSV-ingest time, any UTC offset in the original text was already discarded **before this override step ever runs** — the raw string carrying that offset no longer exists in the registered table to inspect. This diagnostic can only ever detect offset-discarding for a column whose *stored* representation is still `VARCHAR` (i.e., one DuckDB's sniffer left untyped, that a user then overrides to `date`) — recorded as RR-4 below, not silently assumed away.

**A second real DuckDB-WASM run (a post-implementation QA verification pass, not the same review that found the above) caught a further defect specific to the precision-loss check**: the original design assumed `TRY_CAST(x AS HUGEINT)` only *succeeds* for a bare integer literal — false. DuckDB rounds a fractional string to the nearest integer rather than rejecting it, and rounds ties (`.5`) in the OPPOSITE direction from the DOUBLE-cast path (round-half-away-from-zero from text vs. round-half-to-even from a double) — so an ordinary decimal amount like `'1200.5'` (losing nothing as a DOUBLE) was flagged as precision-lossy purely from this rounding-mode mismatch, on exactly the realistic content (mixed money/amount columns) this feature's own motivating scenario involves. Fixed by gating the HUGEINT comparison behind `regexp_matches(text, '^-?[0-9]+$')`, so only genuinely integer-shaped source text ever reaches it.

### Builder responsibility split: authoring-preview-only, not `#11c`'s query resolver

`buildTypedPreviewSql`/`buildCastValidationSql`/`buildCastSampleSql` are documented as this editor's own authoring-time preview/validation surface. `#11c`'s query resolver (queries[] → resolved rows) may reuse the CAST-generation *logic* (`castTargetFor`, the `quoteIdentifier` discipline) but is not assumed to reuse these functions' own call shape verbatim — a resolver's needs (unbounded rows, multi-column joins across `queries[]`) differ from a `LIMIT`-bounded, single-table preview. Left as an explicit non-decision for `#11c` to make with its own requirements in view, rather than silently constraining it now.

## Alternatives considered

| Option | Rejected because |
|---|---|
| `type.toString()` string parsing for category detection | Not a stable API surface; already used for display only elsewhere in this codebase |
| 4+ categories (integer/decimal split, or a `timestamp` category) | Hick's Law; DOUBLE/DATE already sufficient for v0.1's charting use; additive to add later |
| `CREATE VIEW`/`CREATE TABLE AS` materializing overrides | Breaks the existing `DROP TABLE`-based delete contract; loses raw data on a cast-then-recast round-trip; couples this PR to a resolver design `#11c` hasn't made yet |
| `SUM(CASE WHEN ... THEN 1 ELSE 0 END)` for the validation count | PoC-disproven: DuckDB's default `HUGEINT` result doesn't surface as a plain JS number through this codebase's row conversion |
| Two separately-issued raw/typed preview queries, merged by row position | No row-ordering guarantee across two independent `LIMIT` selects without `ORDER BY` |
| Index-derived preview alias trusted without a collision check | Column names are arbitrary data; a real column can legally share the candidate alias's exact name |
| Per-(tableId, column) generation counter alone (no registration sequence) | ABA hazard: a reused table id (post-delete-and-reregister) can let a stale in-flight result look "current" again |
| Per-column preview-freshness gating (reusing the validation generation) | Preview is a whole-row, per-source resource; a different column's later override must be able to supersede an in-flight preview from an earlier one |
| `Source.typeOverrides` as a column-name-keyed object/`SafeRecord` | Reopens the prototype-pollution surface `__proto__`-as-column-name otherwise avoids by never becoming a JS object key |
| Implementing F7 (save/open UI) as part of this PR | Substantially larger scope, no scheduled slot in the M2 kickoff plan sequence; front-loading it here risks a design forced by this PR's needs rather than F7's own |
| Length-heuristic (digit count) for precision-loss detection, instead of a HUGEINT round-trip | Would flag values that actually round-trip fine (e.g. trailing zeros) and miss the exact boundary; the round-trip check is no more expensive and is exact |
| Applying `regexp_matches`/HUGEINT casts directly to the bare column | Real e2e run (Angle D follow-up) proved this throws a binder-time error for a column DuckDB's sniffer already typed as DATE/TIMESTAMP — `CAST(col AS VARCHAR)` first makes both checks well-defined for every column they can actually be called on |
| A full timezone-normalization/conversion model for date overrides | Requires picking a canonical timezone with no universally-correct default; the textual offset-suffix detection surfaces the risk without asserting a judgment call this PR isn't positioned to make |

## Residual risks (accepted for this PR)

- **RR-1 — Date `TRY_CAST` success does not imply correct interpretation.** `TRY_CAST('2024/03/04' AS DATE)` can succeed while silently picking the wrong day/month order — a mistake a pure success/failure count can never surface. Mitigated, not closed: the validation step also samples a few `{original, parsed}` pairs so a user can visually spot-check the interpretation, but a plausible-but-wrong date still looks fine in that sample. Accepted per the plan's own scope decision (non-ISO date format specification is explicitly deferred); revisit if this proves a frequent real-world complaint.
- **RR-2 — `#11c`'s query resolver may need a different CAST-application mechanism than "always TRY_CAST on read."** This PR does not constrain that choice; whichever mechanism `#11c` picks must independently decide how it interacts with a base table this PR guarantees stays unmutated.
- **RR-3 — A large `typeOverrides` array or a wide table could make repeated validation queries noticeable**, even though each fires per-column, on-change (not bulk). No debounce is implemented in this PR; SEC-6 recommended it as a Medium-priority mitigation, tracked as a follow-up if real usage shows it's needed.
- **RR-4 — The timezone-offset advisory cannot detect offset loss for a column DuckDB's CSV sniffer already parsed as a native `TIMESTAMP`/`DATE` at ingest time.** Any UTC offset in the original text is discarded at that point, before this PR's override step (or its diagnostic query) ever runs against the column — the raw string is simply gone from the registered table. The advisory only ever fires for a column whose *stored* type is still `VARCHAR` (left untyped by the sniffer, then manually overridden to `date`) — the realistic common case this feature targets, but not an exhaustive guarantee across every column shape. Accepted: closing this fully would mean either changing what DuckDB's own CSV type inference does at ingest (out of this PR's scope, a `csv-source.ts`-level decision) or reconstructing lost information that no longer exists — neither is a reasonable ask of this PR's own diagnostic layer.
- **RR-5 — The precision-loss advisory cannot detect loss for an integer-shaped string longer than ~38 decimal digits.** `HUGEINT` (the round-trip's exact-comparison type) is 128-bit; a longer digit string casts to `HUGEINT` as `NULL`, so the `WHERE ... IS NOT NULL` guard excludes it from the comparison entirely — a false negative, not a crash. Real government-data ids (postal codes, corporate/invoice numbers, phone numbers) are all comfortably under this ceiling. Closing it fully would require comparing decimal strings directly rather than a numeric round-trip, reintroducing the formatting-difference false-positive risk (leading zeros, sign, whitespace) a numeric comparison was chosen specifically to avoid — accepted as a documented boundary, not solved.

## Consequences

- (+) A postal-code/business-registration-number-shaped column auto-detected as numeric can be corrected to text without losing its leading zero, addressing the concrete real-world failure mode motivating this PR.
- (+) Every CAST-generation code path is provably closed against the type-position injection class that `quoteIdentifier`-style escaping cannot address (fail-fast `castTargetFor`, enum-only schema field, array-shaped persistence).
- (+) The schema gains its first authoring-side per-column shaping contract, ready for `#11c` to build on without a prior migration.
- (+) A "successful" cast can still silently lose information (DOUBLE precision, discarded UTC offset) — both are now actively detected and surfaced as an advisory, not left as an unexamined residual risk, closing the two data-integrity gaps `/code-review` Angle D found in the original validation model (bounded by RR-4 above).
- (−) "Save and reopen preserves the override" is not yet true end-to-end — only the schema half of that promise exists in this PR; the UI half is F7's.
- (−) Non-ISO date formats (a real government-data pattern: 和暦, slash-ambiguous dates) will show as "N件変換不可" rather than being correctly parsed — an explicit, documented scope boundary, not an oversight.
